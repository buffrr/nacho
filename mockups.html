Signing request
screens

Confirmation UI for the four request types. Each screen leads with what is about to happen, states what cannot be verified, and never renders attacker-supplied text as if it were attested.

ref is echoed back untouched and never displayed. A requester-controlled string rendered as a label is spoofable text on a confirmation screen — the mistake origin was making.

Host comes from the endpoint URL, not from an origin field. It's the only domain we can name honestly, because it's where the data actually goes.

exp exists to make stale failures legible, not to stop replay. A QR left on screen while the user wanders off has a dead session behind it — "this request expired, refresh the page" beats an unexplained failure.

No endpoint means the requester can't consume a POST. Don't show a Send button that will 404 — the result screen offers copy only. No domain, no source row, nothing to spoof.

03

Zone changed at approval

We resolve on approve, not on scan — so the diff shown was computed against a cached zone. If the live zone differs, re-show and require a second tap.

9:41▮▮▮
‹Records changed
↻This handle changed since we showed you the last screen. Here's what would actually happen now.

A request asks to replace

wasaddr · btc

bc1q9dfp0s2m7yqm4l0ke34xxa2

nowaddr · btc

bc1qar0srrr7xfkvy5l643lydnw9re59

Publish anyway
Cancel

The gap is user-controlled and can be minutes. Without this step a stale request silently clobbers a change made from another device — and the case where it matters most is exactly the case where the user was already editing that record.

Costs one extra tap in the rare case. In the common case the recomputed diff matches and this screen never appears.

Chunked, never raw hex. The recipient key is the one field a user must actually verify, so make verifying it possible.

Signing doesn't move the handle — broadcasting does. The signature is a bearer instrument, so the warning is about the broadcast, not the tap.

Payloadsaleonly price comes from the requester
{
  "v": 1,
  "type": "sale",
  "handle": "nzjsk@test10000",
  "price": "500000",        // ₿500,000
  "outpoint": {
    "txid": "9b2c…41ff",
    "vout": 0,
    "amount": 100000000
  },
  "ref": "v18kL2", "exp": 1786291400
}

// Payout address is NOT in the payload.
// Prefilled from the user’s own addr:btc record.

Name the amount inline. "Whoever completes this transaction" is vaguer and buries the number that makes the sentence concrete.

Don't name the auth method on the button. Face ID, Touch ID, fingerprint, face unlock, and PIN all vary by platform, device, and what the user enrolled. The system prompt already says which one it is.

₿-only format per BIP-177 — integers, no decimals, no "sats". ₿500,000 reads instantly where 0.00500000 BTC does not.

The payment output is input + price, so a ₿100,000,000 handle sold for ₿1 pays out ₿100,000,001. Never show that as what the user receives — the price is the headline number.

Rules the screens encode

  • Never render a claim as a factPayload-supplied names are free for an attacker to set. Only the host derived from an endpoint URL is nameable, because it's where data will actually go.
  • Warn about exceptions, not normsAn amber banner on every request stops being read within a week. Inert records get no warning so that value-bearing ones still land.
  • Show the payload, not a summaryThe thing being judged is the largest element on screen, in monospace, in full. Counts hide destruction — replaces show both values.
  • Warn about consequences, not infrastructure"We can't verify the outpoint" explains our gap, not the user's situation. What matters is that broadcasting is irreversible — say that instead.
  • Consequence sets the frictionInert record: one tap. Address record: recognition checkbox. Sale: full-screen confirmation plus device authentication.
  • No protocol vocabulary"Transfer handle", "Sell handle", "Sign in". PSBT appears only as the label of the copyable blob and in dev docs.
